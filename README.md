### Java / Spring 백엔드 개발자

맡은 기능을 만드는 데서 끝내지 않고, 배포와 운영을 거쳐 현업에서 실제로 쓰이는 데까지 챙깁니다. 백엔드에서 시작했지만 필요할 때마다 테스트와 배포, 인프라, AI와 함께 일하는 방식까지 범위를 넓혀 왔습니다.

`Java` `Spring Boot` `JPA` `PostgreSQL` `Redis` `AWS` `Terraform` `Jenkins`

#### 이런 문제를 풀어 왔습니다

- **결과를 알려 주지 않는 외부 연동**: 타임아웃은 실패가 아니라 "모름"입니다. 병원 진료 시스템(EMR) 예약 연동에서 업체 API에 멱등키가 없고 의료진도 같은 예약을 고쳐서, 재전송은 중복 예약이 되거나 사람의 최신 수정을 덮어쓸 수 있었습니다. 그래서 요청을 기록하고 커밋 뒤에 보내는 데까지만 아웃박스를 따르고, 자동 재전송은 빼고 조회로 결과를 확인할 수 있는 요청만 재처리하게 했습니다.
- **돈이 오가는 데이터의 정합성**: 복지포인트 대량 지급에서 먼저 따진 것은 "원장을 쓰고 처리 상태를 기록하는 사이에 서버가 죽으면 무엇이 남는가"였습니다. 그 틈을 없애려고 둘을 한 트랜잭션에 넣되, 한 사람의 실패가 다른 사람의 지급을 되돌리지 않도록 원자성의 단위는 배치가 아니라 사람으로 잡았습니다. 멱등키가 같아도 내용이 다른 요청은 같은 요청으로 받지 않았고, 마지막 방어는 DB unique 제약에 뒀습니다.

#### 팀이 빠르면서도 안전하게 일하도록

AI 덕분에 코드는 빨리 나옵니다. 그만큼 잘못된 결과가 나가지 않게 막는 장치가 더 중요해졌습니다. 이 분야는 좋은 방법이 계속 바뀌어서, 지금 방식을 정답으로 두지 않고 팀에 먼저 제안한 뒤 써 보면서 고쳐 왔습니다.

- **검증을 사람 대신 CI에**: 테스트가 CI에서 돌지 않아 실패해도 배포가 막히지 않았고, 외부 AWS와 개발 DB에 묶여 있어 환경에 따라 결과가 달랐습니다. 의존을 테스트용 대체와 컨테이너로 옮겨 어디서 돌려도 같은 결과가 나오게 한 뒤 PR마다 돌게 했습니다. 여러 팀이 함께 쓰는 빌드 노드에서 배포가 밀리던 문제는 반복 빌드를 9~10분에서 2분대로 줄여 덜었습니다.
- **AI가 읽을 맥락은 정확하게**: 에이전트는 오래된 문서를 근거로도 그럴듯한 코드를 만듭니다. 지침에서 코드와 어긋난 서술을 고치고 코드에서 읽을 수 있는 내용은 빼, 틀린 맥락으로 작업할 여지와 에이전트가 매번 읽는 토큰을 함께 줄였습니다.
- **사람이 볼 것과 AI가 볼 것**: AI가 만드는 속도를 사람의 리뷰가 따라갈 수 없다고 보고, PR을 계획 단위로 잘게 나누자고 팀에 건의했습니다. 반복되는 지적은 AI가 읽는 리뷰 기준과 심각도 태그로 옮겨, 사람은 설계 판단을 보게 했습니다.
- **가드레일**: 막을 대상은 "되돌리기 어려운가"로 골랐습니다. 에이전트의 배포 push와 AWS 쓰기 명령은 훅에서 막고, 판정하지 못한 명령은 통과가 아니라 사람 확인으로 넘겼습니다. 마이그레이션 버전 충돌과 공개 API 규칙 위반처럼 리뷰에서 놓치기 쉬운 것은 PR 검사가 잡습니다.

#### 부족하다고 느낀 부분은 이렇게 채웠습니다

- **클라우드 운영**: AWS Solutions Architect Associate를 취득한 뒤 서버 운영에 참여했습니다. DB 커넥션이 고갈됐을 때 알림은 왔지만 원인 세션을 찾을 기록이 없던 것을 계기로, 락 대기와 느린 쿼리 로그를 남기고 끊겨 있던 DB 알람을 Terraform으로 다시 연결했습니다.
- **컨테이너**: 빌드 캐시를 고치다가 컨테이너를 더 깊이 알아야겠다고 느껴 CKA를 취득했습니다. 이후 배포가 롤백됐을 때 원인이 코드가 아니라 헬스체크 유예 시간이라는 것을 로그로 찾았습니다.
- **생성형 AI**: 관리형 AI 플랫폼은 AI 서비스가 지켜야 할 것(평가, 비용, 보안, 가드레일)을 기능으로 묶어 둡니다. 그 구성을 거꾸로 공부하면 직접 만들 때 무엇을 챙겨야 하는지 알 수 있겠다고 보고 AWS Generative AI Developer Professional을 취득했습니다. 배운 것은 아래 두 AI 프로젝트에서 평가셋을 만들어 직접 확인했습니다.
- **실무에서 겪기 어려운 규모와 구조**: 서비스를 나눈 뒤의 정합성, 배치의 재시작과 누락처럼 회사에서 만나기 어려운 문제는 아래 프로젝트로 직접 재현해 봤습니다.
